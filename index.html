A practical operating system for building with AI

The Vibe Coder's Playbook

Written for people who build with AI, test like humans, and refuse to ship garbage. Not theory — every rule here was learned by breaking something real.

Who this is for

You, if any of these are true:

  • You build things with AI as a partner and you're honest about it
  • You can read and edit HTML, JSON and configs, but you're not a "10× systems engineer"
  • You care more about the product working than the code being fancy
  • You have watched AI confidently produce something beautiful and completely broken

Then congrats — you're a vibe coder. This playbook makes you a professional one.

The core identity

Vibe Coder = Director + QA Lead + Refiner

Director
You decide WHAT gets built and what "good" means.
QA Lead
You test every flow like a suspicious first-time user.
Refiner
You fix wording, spacing and flow until it feels effortless.

You are not a language model's typist. If AI wrote it, you still own it — including its bugs. That's the whole professional mindset in one line.

The 10 rules

  1. Define "done" before you prompt

    Write 3–5 bullet acceptance criteria before asking AI to build: "It must go full-width on mobile, clicking downloads a file, console stays clean." If you can't describe done, AI will happily build never-ending.

  2. One feature per prompt

    Big prompts create big messes. Build in slices that each end with something you can open and test.

  3. Test like a suspicious user

    The moment code "runs", your job starts: feed it wrong inputs (empty, huge, weird characters), check it at mobile size, click every button, read the console.

  4. Never ship what you haven't clicked

    Untested AI code is a rumor, not a product. Click it. All of it.

  5. Keep a "known issues" list

    Every project gets a KNOWN-ISSUES.md. Honesty compounds; pretending doesn't.

  6. Small fixes, commit fast

    One fix = one commit = one clear message. Future-you will send thanks.

  7. When AI spirals, cut your losses

    If a fix fails three times, stop. Re-explain the problem from scratch — fresh context beats arguing with a confused model.

  8. Read the diff, not the vibes

    Before accepting AI changes, actually look at what changed. Green-checkmark energy is not verification.

  9. Be honest about your stack

    "I built this with AI, tested it by hand" is a strength in 2026 — clients and open-source communities value shipping plus judgment. Fake skills collapse in the first technical interview. Real process scales.

  10. Leave it better

    Every session: fix one papercut, improve one line of text, delete one dead thing. Small refinements × time = pro-level products.

The loop (daily driver)

  1. Idea — ask yourself: what problem, and for whom?
  2. Criteria — 3–5 bullets of "done"
  3. Prompt — one small, context-rich task
  4. Test — suspicious-user mode: click everything
  5. Note — what broke goes into KNOWN-ISSUES.md
  6. Fix — one fix at a time
  7. Ship — commit + deploy
  8. Refine — tomorrow's phase one

Prompt template that works

prompt.txt 
Context: This is a [type] that [purpose]. Right now [current state].
Task: Make only [one specific change].
Keep in mind: [brand/style constraints].
Definition of done:
- [criterion 1]
- [criterion 2]
- [criterion 3]
Also: do not create any new file without telling me.

Common failures (all personally witnessed)

FailureCure
"AI said it works"It works when you open the browser.
Feature soupOne prompt = one feature.
Two competing truths in the codeDelete the old one. Never keep both.
Mobile layout guessedDevTools → device toggle → actually look.
Beautiful but brokenRule #3: suspicious-user test.
Shiny-object syndromeZero the known-issues list first, new features after.
